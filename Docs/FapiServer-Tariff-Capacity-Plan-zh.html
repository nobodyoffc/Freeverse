§1

你实际在为什么付钱

一个 FapiServer 节点跑五个进程：Elasticsearch、Docker 里的 Freecash 全节点、FchParser、FeipParser，以及监听 UDP 8500 的 FapiServer 本身。它们的成本特征完全不同，而真正影响账单的只有两个。

内存——你花钱买的东西

Elasticsearch 是绝对大头。它要吃掉半台机器作堆内存，另外半台作页缓存。Freecash 节点、两个解析器和 FapiServer 加起来还要 5–6 GB。这就给单机部署划出了 16 GB 的下限，也让「每美元买到多少内存」成为选型时该盯的指标。

出站流量——随规模增长的那一项

FUDP 发给手机的每一个字节，都会在某处被计量。AWS 上是 $0.09/GB；欧洲平价主机上是 $0.001/GB；带不限量千兆口的独服上则是 免费。同样的字节，80 倍的价差。这一个选择所左右的金额，超过本文其余所有决策的总和。

存储——便宜且增长缓慢

Freecash 出块间隔约 1 分钟，且区块大多是空的。340 万个区块在磁盘上只占个位数 GB；由此构建的 ES 索引在无副本时约 15–30 GB，每月增长远低于 1 GB。真正随用户增长的只有 DISK 和 DOCK 的载荷存储，而那部分有自己的计费项。

你的时间——没人给你开发票的成本

非托管 VPS 账单更便宜、工时更贵：没有快照即服务、没有托管备份，硬件故障归你处理。1 万用户规模下，各家主机的账单差距是 18 倍；把每月 2–5 小时按 $50/小时计价后，差距塌缩到 2.6 倍。两个数字都真实，但只有后者够格用来做决策。

计费字节与账单金额之间的差额

FAPI 计量的是 FUDP 载荷，主机商计量的是离开网卡的字节。两者之间差着一个可预测的系数：

FUDP 头部 + 加密包 …………… 每个 1350 字节数据报 73 字节
IP + UDP 头部 ………………… 28 字节
ACK、重传、路径探测 ………… 通常 ~5–12%
────────────────────────────────────────
链路字节 ≈ 1.20 × 可计费载荷字节

重传的字节是刻意不向客户端重复收费的，但主机商照收不误。下文每一个容量数字都同时给出两种单位：计费字节（你开给客户的）和 链路字节（主机商开给你的）。

结论

不要把自己绑死在一家主机上。随着服务器成长，换档。在 T1 之前，账单只是噪音——$19 的机器和 $74 的机器是同一个决策，那就买最省你工时的那台。从 T2 起出站账单开始有分量，平价档开始物有所值。到了 T3，用不限量独服跑数据面、再配上多个区域云边缘节点，比 Lightsail 便宜 4 倍、比 EC2 便宜 14 倍，而那时的业务量也足以支撑相应的运维投入。

AWS 仍然值得付费的地方

有两件事，无论服务器本身跑在哪里都成立。用于备份的对象存储——余额账本、它的 WAL 和审计日志从第一天起就该放进 S3 或 Backblaze B2，无论算力在哪，这项开销都只有每月一美元左右。以及亚太覆盖，如果 Freer 的用户在那边的话：Hetzner 只有一个新加坡区且流量条款差得多，而 AWS、Vultr 和 DigitalOcean 都有东京、首尔和悉尼。对一个 UDP 协议来说，延迟和可达性比一张便宜的账单更值钱。

§5

定价

价格必须依次越过四道门槛：字节的边际成本、按流量摊薄的机器固定成本、从收入顶端被抽走的推荐分成，以及一份用于积累储备金的毛利。

1 · 边际底线——多发一个 GB 的成本
超大规模云 $0.090/GB · 含流量包云 $0.010 · 平价云 $0.001 · 独服 $0.000

2 · 加上固定成本，按目标规模的可计费流量摊薄
价格 = ( 每月全成本 ÷ 可计费 GB ) × ( 1 + 毛利率 ) ÷ ( 1 − 渠道分成 )

3 · 取 T2、中位主机、30% 毛利、20% 消费渠道分成
$379 ÷ 2,500 GB × 1.30 ÷ 0.80 = $0.246 / GB
……而同一算式用在 T2 最便宜的主机上得到 $0.152 × 1.625 = $0.247
……用在 Lightsail 上则是 $0.191 × 1.625 = $0.311

4 · 向下取整为一个站得住脚的挂牌数字
pricePerKBOut = $0.20 每 GB = $1.907 × 10⁻⁷ 每 KB

从算式结果向下取整是刻意为之。$0.246 是恰好在 1 万用户处收回全部成本的价格；$0.20 则在约 1.2 万用户处收回成本，并留出成长空间。它同时是超大规模云边际费率的 2.2 倍、平价云费率的 200 倍——这才是诚实的价差：你卖的绝大部分不是原始带宽，而是一个吃内存的数据库和两个不管有没有人查询都在跑的解析器。

由此引出两处调整。所有主机的入站流量都是免费的，所以入站定价只需覆盖一次上传引发的 CPU 与磁盘写入；取出站费率的 20%，既能遏制滥用，又不至于惩罚上传。已存储的字节只要还在那里就一直占磁盘——$0.10/GB·月 高于 AWS gp3 的 $0.08，更远高于磁盘随套餐赠送的 Hetzner 机器，而这部分差价正是用来给这些字节做备份的。

因为成本是阶跃函数而收入是一条直线，服务器在每次升级之后都会短暂地陷入亏损。这意味着应当尽量晚升级：平价主机上的 T1 机器带 20 TB 流量额度，相当于 6.5 万典型用户的流量。那里真正的瓶颈是 CPU 与报文数，不是带宽，所以该由并发数——而不是带宽曲线——来触发升级。

§7

折算为 FCH

上面的资费以美元计，因为账单以美元计。而服务声明要的是每 KB 多少 FCH。一个公式即可打通：

每 KB 聪数 = 95.367 × ( 每 GB 美元价 ) ÷ ( FCH 的美元价 )
每 KB FCH  = 每 KB 聪数 ÷ 100,000,000

该常数为 10⁸ ÷ 1,048,576——即每 FCH 的聪数，除以每 GB 的 KB 数

按推荐的 $0.20 / $0.04 / $0.10 资费，在四种汇率下的结果：

调价不是免费的，所以节奏比精度更重要。价格存放在链上服务声明中，在服务器启动或手动刷新时读取，并被每一个客户端缓存。每月复核一次，只在汇率变动超过 30% 时才调价，并在交易上链之前于应用内公告。两次复核之间由毛利吸收漂移，这也正是那 30% 存在的部分理由。

两个方向的伤害各不相同。如果 FCH 下跌，美元收入随之下跌，在你调价之前一直亏损。如果 FCH 上涨，你实际上是在超额收费，而带 maxPayment 保护的客户端——FC-JDK 客户端默认在超过 1 FCH 时停止自动充值——会开始拒绝续费。同一套按月纪律可以同时解决这两种情况。

§8

由此引出的配置修改

当前的测试声明把所有项都定为每 KB 1 聪——在任何合理的 FCH 汇率下，这都不到成本的百分之一的零头。有四项设置必须一起改动，其中还有一项无论价格如何都会阻塞上线。请按 §7 用你发布当天的汇率计算 FCH 数值。

"creditLimit"        10000     →  与 minCredit 对齐，单位为聪
"maxTotalDiskUsage"  10 GB     →  按档位设定（§3）
"minDealerBalance"   1000000   →  按数个结算周期的规模设定
当前配置中的三个陷阱

信用额度只够一千字节。creditLimit 是 10,000 聪。在任何现实价格下，一个全新用户大约只能用 1 KB 就会撞上 402 PAYMENT_REQUIRED。FapiBalanceManager 在启动时就会针对这一点打出警告——不要带着它上线。另请注意 service.minCredit（以 FCH 计）会覆盖 settingMap.creditLimit（以聪计），所以只调其中一个是无效的。

home.api 指向的是 Android 模拟器。10.0.2.2 是模拟器对宿主回环地址的别名。一旦这样发布到链上，任何真实设备都无法访问该服务。声明发出去之前，这里必须换成公网主机名。

minPayment 还是按旧价设的。0.01 FCH 在新资费下只能买约 150 KB，会导致每隔几分钟就触发一次自动充值交易。应当把它设为典型用户约一个月的流量。

一处值得改的代码

FapiBalanceManager 的免费列表初始包含 PING、PONG、PEER_INFO 和 CHAT_ACK。map.register 不在其中，而费用按 ceil(bytes/1024) × price 计算——于是一个 250 字节的 NAT 保活包被按整整一千字节计费，虚增四倍，每 25 秒一次。一个每天在线三小时的用户每月要发出约 13,000 个这样的包，被按 13 MB 收费，而实际只有 3 MB——约占其账单的 5%，而这全部是为了一个只为撑开防火墙而存在的报文。

要么把 map.register 加入默认免费集合，要么按字节而非取整的千字节计费。前者是一行改动，也是更诚实的做法；保活包是基础设施开销，不是用户主动请求的服务。

§9

风险与其他因素

最要紧的那一条

FCH 收入付不了主机账单。Freecash 在三个市场交易，日成交量近乎为零。资费赚到的一切，都以一种无法在任何价位可靠卖出的代币形式到账。请把服务器规划成一项以美元供养、以 FCH 计量的运营：持有覆盖 6–12 个月主机费用的美元储备，并把 FCH 收入当作生态内的信用额度——可用于支付其他 FAPI 服务商、购买 DISK 空间、与利益相关方及渠道结算——而不是当作营收。在 FCH 拥有真实市场之前，§6 中每一个盈利数字在算术上都正确，在经济上都只是理论。

廉价主机会封停中继

ROAD 在对等节点之间转发不透明字节。那就是中继，而中继无论实际转发的是什么，都会招来滥用投诉。低价与平价主机对投诉的处理是先动手后问话；超大规模云则有正规流程。这是迁离 AWS 时最大的非价格风险。缓解手段：FAPI15 中已有的 2 跳上限、按对端的中继限速、公开的滥用举报联系方式，以及一条演练过的迁往备用主机的路径。

今天的价格不是明年的价格

Hetzner 在 2026 年调价两次——4 月最高上调 37%，6 月 CPX 与 CCX 系列上调 113–175%。Oracle 未经公告就把免费套餐砍半，并终止了超出新限额的实例。不要建立一个只在某一家主机当前价目表下成立的模型。§5 的敏感性表格存在的意义，就是让你在任何一家主机下次涨价后能重新推导价格。

免费额度是女巫攻击的目标

每个新 FID 都能拿到信用额度，而 FID 是可以免费铸造的。把试用额度控制在几百 KB，任何更慷慨的额度都要绑定到有链上历史的 FID，并按源地址对新账号创建限速。按每个身份 150 KB 计，一千个假身份只让你损失约三美分——这正是合适的量级。

UDP 暴露面

8500 端口对公网开放，且会响应未认证的报文。AWS 免费提供 Shield Standard；Hetzner 和 OVH 自带 DDoS 过滤；Contabo 的就薄弱一些。无论用哪家主机，都要在 FapiServer 上加按源地址的报文速率限制，并对每个对端每分钟的 road.relay 设上限——应用层的限制才是你在任何地方都能掌控的那一层。

Docker 镜像来自 2021 年

freecash v1.0.5 于 2021 年 2 月以镜像存档形式发布，几乎可以肯定只支持 amd64。这就排除了用 ARM 实例跑节点的可能——而 ARM 恰恰是每美元内存最划算的地方（Hetzner CAX41 用 $48 给 32 GB）。用 docker image inspect --format '{{.Architecture}}' 验证。如果确是 amd64，要么全程留在 x86，要么只把节点放在 x86，而把 ES 和 FapiServer 放到 ARM 上。

你的用户在哪里

Hetzner 有德国、芬兰、两个美国区和新加坡——而新加坡的流量条款差得多。如果 Freer 的用户集中在亚洲，平价档的吸引力会大幅下降，含流量包的云（Vultr、DigitalOcean、Lightsail）凭借东京、首尔和悉尼的节点胜出。对一个 UDP 协议来说，可达性与 RTT 比账单差额更值钱。

余额账本就是钱

LevelDB 余额库、它的 WAL 和审计日志，是每个用户付了多少钱的唯一记录。丢了它们就等于丢了余额和结算能力。每天异地备份到对象存储，保持审计日志的哈希链完整，并在真正需要之前先演练一遍「快照 → WAL → 审计」的恢复路径。这是唯一一份无法通过重放链数据重建的状态——也是无论算力放在哪里、都值得在超大规模云保留一只脚的最有力理由。

DISK 的存储分层

DISK 载荷放在 AWS gp3 上是 $0.08/GB·月；同样的数据块放在 S3 Standard 上是 $0.023，且传输到同区域实例免费。在平价主机上，磁盘随套餐赠送，在用尽之前基本等于免费。无论哪种方式，字节最终仍然要经 FapiServer 发出，出站成本不变——这只影响存储那一行。

预付折扣

如果你确实要留在 EC2，1 年期无预付的 Compute Savings Plan 大约能给算力打七折，3 年期约打五折。它对出站流量毫无帮助，而那正是真正疼的一行。Lightsail、Hetzner 和 Contabo 没有预付折扣，也不需要；独服则改为收一次性上架费，上文已按 12 个月摊销。

链上运行开销

结算每 14,400 个区块（约 10 天）执行一次并广播分账；充值检测需要一个有余额的收款地址；修改资费本身也是一笔交易。Freecash 的手续费可忽略不计，但收款地址需要常备浮存——minDealerBalance 目前是 0.01 FCH，应当按数个结算周期的规模来设定。

竞争对手决定价格上限

客户端从链上发现 FAPI 服务商，并能在连接前读到每一家的价格。除了服务质量所能支撑的部分之外，你没有任何定价权；每次调价前都应把推荐费率与别人挂牌的价格对照一遍。运营参考实现带来的优势在于信任，而不在于价格。

增值税与结算摩擦

欧洲主机商报价不含增值税。欧盟以外的客户无需额外支付；没有增值税号的欧盟个人消费者要额外付 19–20%，这会抵消掉平价档的一部分优势。独服还带一次性上架费——AX42 约 $62——而且多数平价主机在卖给你大配置机器之前会要求身份验证。

§10

运营节奏

模型的质量取决于输入，而其中有三项目前只是猜测——服务器自己在有了一个月真实流量之后就能用实测值替换它们：每用户字节数、链路与计费字节之比，以及峰值并发。

按月跟踪

  • 可计费的入站与出站 KB 数，取自 EconomicsMetricsCollector——与主机网络计数器给出的链路字节对照。二者之比就是你真实的开销系数；本文所用的 1.20 只是一个估计值。
  • 每交付 GB 的成本，分别按账单和全成本统计。这是价格必须跑赢的数字，且应当随用户增长逐月下降。
  • 花在服务器上的工时。本文中最被低估的一行，而在 T3 以下的每一档上它都是最大的一行。
  • 每月活用户的 FCH 收入，以及按当月汇率折算的美元值。两条独立的序列，不要混在一起。
  • 核销掉的信用额度——余额为负且再未充值的账户。这才是免费额度的真实成本。
  • DISK 与 DOCK 的 GB·天存储量，对照存储收入，确认已存储的字节能覆盖自身成本。
  • 峰值并发对端数与每秒报文数，这才是真正触发下一次升级的指标——不是带宽。

按季度决策

  1. 若汇率自上次调整以来变动超过 30%，则重新以 FCH 定价（§7）。
  2. 若任一主机的价目表发生实质变化，或你自己的小时单价变了，则重新推导美元价格（§5）。
  3. 在峰值 CPU 超过 70% 或 ES 堆压力成为常态时升级——而不是在带宽用尽时，那要晚得多。
  4. 用实际的第三方推荐量重新核对渠道分成设置（§6）。
  5. 将 ES 与节点磁盘的实测值对照预测重新测量，并在卷用到 80% 之前扩容。
执行顺序

先修 §8 里的配置陷阱和 home.api 主机名——不管价格怎么定，它们都会阻塞上线。把资费放在同一次链上更新里发布，让客户端看到一次连贯的变更。试点跑在满足 §3 需求的最便宜机器上，因为在那个规模下账单无关紧要，唯一真实的成本是你的注意力。然后让上述指标取代 §3 中的假设，在 T1 升级之前用你自己的数字重新推导价格。
